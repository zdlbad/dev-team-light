# UI 设计：写的样子

想清楚的东西怎么写下来。怎么想，在上一层文件夹的 `UI 设计.md` 里；这一份你想完、动笔之前读：读你要写的那种文件的那一块，写完照那一块核一遍。

## 每种文件

**上下文/<名>/界面/<需求编号>.json**（一条需求一份；一条需求跨了几个上下文，哪个上下文里有它的屏，就在哪个上下文下放一份，文件名都用需求编号）

```
{ req, title,
  views: [{ who, screens: [{ id, title, file, step?, shows: [字段], does: [{ act, to, note? }], asks?: [{ id, q, lean, options, answer?, answeredAt? }], finds?: [一句需求候选], decidedAt? }] }],
  flow?: 流程名 | [流程名] }
```

views 一个视角一项，who 是参与方的叫法；screens 按操作先后排；屏 id 在一条需求里不重复；file 是这一屏的小样文件名，文件放在 `<需求编号>/` 这个文件夹里；does 的 to 是这一份里任何一屏的 id 或「完」，指到别的视角的屏就是交棒；step 是这一屏对应 flow 那段流程的哪一步，一条需求跨几段流程时 flow 写成数组、按先后排，step 写「流程名/步号」；asks 是画的时候没说清的，id 在一条需求里不重复（a-1、a-2…），options 两到三个、第一个是你偏向的，人答了写进 answer，你照着改屏，改完把这条问题删掉、连同 html 里它的 data-ask（答案在日志里有，屏上只留没答的）；finds 是发现的需求候选；decidedAt 是人定下这一屏的日期，没定的不写；定过的屏，你改了它的交互或者内容，就把这一屏的 decidedAt 去掉，人要重新按。

一条需求跨了几个上下文时，每个上下文下的那一份只放这个上下文里的屏，to 也只指这一份里的屏；这一次做哪个上下文的屏，派工书会写明。操作走到另一个上下文那边去的那一段，这一份里不画屏：你在交出去的那一屏的 does 里加一条，act 用括号写那边的人做了什么，to 指向回到这边以后的那一屏，note 以「交棒：」开头，说明那一段在哪个上下文的小样里。

**上下文/<名>/界面/<需求编号>/<屏 id>.html**：单开能看的一屏，写死数据，按钮能跳到下一屏。问题说的是屏上哪个东西（一个输入框、一个下拉、一块列表），就在那个元素上写 `data-ask="a-4"`（几条说同一处用空格隔开：`data-ask="a-4 a-5"`）；不对着某个东西的问题（这一屏算不算、整屏怎么排）不标，页面把它放在这一屏右上角。

**页面「界面」**：左边栏 上下文 › 需求 › 视角 › 屏，定过的屏标日期；主区页头是需求和已定几屏，下面一排视角切换，再下面是这个视角的屏序列；嵌着这一屏的小样，按到交棒就切到那个视角；旁边列谁在用、显示什么、能按什么、问了什么（问题钉在小样上：标了 data-ask 的元素旁边一个带编号的红点，没标的在屏右上角；点红点弹出气泡，带偏向和选项，点一个就是答了，答案写回这条需求的 json；答了的变灰点、可以收起；旁边一栏也照样列）、发现了什么；左边栏需求和屏那行红点加还有几条没答；当前屏旁边「定下」。这一页的页面代码在这支队目录的 `pages/界面/`。

定下一次定一屏，记在这一屏的 decidedAt 上。
