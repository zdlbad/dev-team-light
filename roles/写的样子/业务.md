# 业务：写的样子

想清楚的业务怎么写下来，别人才看得懂。怎么想业务，在上一层文件夹的 `业务.md` 里；这一份你想完、动笔之前读：先读「写法上的思想」和「还在攒的经验」，再读你要写的那种文件的那一块，写完照那一块核一遍。文件里细的问题答不上的，回原料去查，不凭印象写。

## 写法上的思想

- 你用做业务的人自己的说法来写，不用系统的说法，也不自己另起名字。比如写「照护伙伴把服务记录记到她名下」，不写「系统创建记录」；原料上印着名字的东西，就用原料印的那个名字。因为后面的人是拿着原料、照做业务的人的叫法来找东西的，名字对不上就找不到。
- 业务文件是交给人确认的，每一处只放要他确认的那一样东西。因为别的东西挤进来，要确认的那一样就被埋了。所以规则那一句只写结论，这条规则是怎么来的放进出处；步骤旁边只写业务规则和需要特别考量的逻辑，步骤本身已经说了的事、你为什么这么画、这一步出自原料哪里，都不写在那里，步骤上看不出来的前提条件照旧记成一条规则；实现的细节不写，只写用的人看得到的结果，比如「改完以后大约半分钟内各处都生效」，你从代码倒着读的时候碰到的实现细节，交回时列给建模，由建模写进属性的备注或聚合的规则。
- 同一件事只记在一处，别处要用就指过去。因为记在两处，以后有人改了其中一处，另一处就和它对不上；看的人也会以为是两件事。比如界面的小样上已经看得到的、概念图里已经定义过的，流程里不再写一遍；同样两样数据之间，概念图上只画一条线，两边的关系都写进这一条线的 label。

## 还在攒的经验

- 核心数据的来路是从别的主题进来的，起点就写那个主题里发生的那件事，比如「订单那边一张订单确认了」，写上 event: true 和 topic（那个主题的名字，写法和去处的一样），别的主题里的数据不画成这里的一站。因为那些数据归那个主题，画进来就把上游的业务当成了这个主题的业务。
- 只是读了核心数据的事不算它的去处，写进读它的那项功能的要用到的数据。
- 流程里的参与方，你写原料里的角色，不写具体是哪家公司。因为公司会换，分包关系会变，角色不变。你按公司来画，同一个角色就会被拆成好几列。
- 核心数据的看板上，op 改状态、作废、撤销、换挂靠、往里补一条，都写更新；只有那份数据真的没了，才写删除。
- 流程是时序图，只画人和人之间的交接，主题和系统都不画成参与方的一列。系统到了时间自己做的事不画进流程，写进模块业务的内部流程。
- 补一项功能，你回头查四处：有没有一条更细的目的挂上了它；它动的那样核心数据，来路或去处写了没有；主要流程速览里该不该有这一步；流程文件里对应的那一步写了没有。

## 每种文件

一种文件一块。每一块里先是文件的骨架，再是这种文件要答的问题和每一栏怎么写，最后是和工作台之间的约定：编号怎么起、哪几栏只为页面摆放才写、页面怎么显示、检查工具查什么、人在页面上答了以后怎么收。页面改了，这几条约定跟着改。

出处（source）在各种文件里写法一样：照他的话写出来的内容，出处写他是哪一天说的，再加上他的原话；照需求写出来的内容，出处写需求的编号。

**上下文/<名>/业务/全局图.json**

```
{ background,
  topics: [{ id, title, c, x, y, does: [两句], concepts: [数据名] }],
  edges: [{ from, to, label }] }
```

要答的问题：

- **整个上下文所处的情形是什么？**（background）用一两句话写整个上下文的背景。
- **这个上下文的业务分成哪几个主题？**（topics）每个主题做什么，写两句（does）；它手里有哪些数据（concepts）。
- **主题之间主要有哪些业务交流？**（edges 的 label）一件事只是读了另一个主题的数据、是它的上游来源、或者结果会让它跟着变，这三种关系不算归属，你画成全局图上主题之间的线，在 label 里说清是读取、是来源，还是结果带来的变化。

和工作台之间的约定：

- 只为页面摆放写的栏：c 是颜色号 1–5；x、y 是格子位置，从左到右、从上到下是发生的先后。
- label 用「；」分句。
- 页面怎么显示：background 页面放在全局图的上面，下面列出每个主题的业务目的，业务目的从各主题的模块业务里取。

**上下文/<名>/业务/概念/<主题>.json**（一个主题一份）

```
{ topic, title, summary,
  concepts: [{ id, title, by: [角色], order, definition, source, fields?: [栏名], nudge?, table?: { columns: [列名], rows: [[一格一格]] } }],
  external: [{ id, title, topic, context? }],
  edges: [{ id, from, to, label, by?: [角色], source?, tree? }] }
```

要答的问题：

- **这个主题自己有哪些数据？**（concepts）每样叫什么（title）、谁经手（by）、怎么定义（definition）、出自原料哪里（source）。一样数据上面有哪些栏，你列进 fields，一栏一个名字，帮人理解它是什么；不把每一栏单画成一个概念，单个栏本身是业务概念的才单列，照角色文件里的判法。一个栏能取哪些值不写进来。
- **有没有一样东西要按几类人或几种情形逐行对照？**（concepts 的 table）比如每个角色进得了哪些页、做得了哪些事。有，就在那个概念上加 table，第一列写是哪一类。
- **它连着别的主题里的哪些数据？**（external）别的上下文里的、共享内核里的也写在这里。
- **这些数据之间是什么关系？**（edges）关系写在 label 里，by 是做这件事的角色。
- **谁装着谁？**（edges 的 tree）一样数据装着另一样的，画一条上下层的线：tree 写 true，from 装着 to。核心数据装着的概念都用这种线连到它，一层层往下；同一个概念装在两样核心数据下面的，两处都连。因为页面照这些线把概念一层层套在核心数据里面，线没有连上的概念落在外面，看的人就不知道它归谁。模块业务里核心数据的 parts 要和这些线对得上。
- **用到的资料是谁在用？**（edges）用到的资料和用它的那个概念之间，连一条不是上下层的线。页面照这条线把资料列在那样核心数据下面。
- **分了子主题的主题，有哪几个子主题？**（subs、edges）每个子主题做什么（does）、手里有哪些数据（concepts），子主题之间有哪些业务交流（label），问法和全局图一样。
- **共享内核里有哪些概念？** 问法和概念图一样。

和工作台之间的约定：

- 只为页面摆放写的栏：先后由线算出来，order 定同一列里的上下；nudge 是一个数，把这个框在图上往上或往下挪几个像素，只有图上挤了才写，备注不写在这里。
- external 里，别的上下文的写上 context（上下文名），共享内核的 topic 写「共享内核」。
- 页面怎么显示：table 页面画在概念图下面。
- 检查工具：fields 不是一列栏名的，检查工具报错。同样两样数据之间有几条线、核心数据的 parts 和上下层的线对不上、概念图上的概念在模块业务里没有出现，检查工具会提醒。

**分了子主题的主题**：`概念/<主题>.json` 改成子主题图，形状照全局图：

```
{ topic, title, summary,
  subs: [{ id, title, x, y, does: [两句], concepts: [数据名] }],
  edges: [{ from, to, label }] }
```

每个子主题一份 `概念/<主题>/<子主题>.json`，形状和上面的概念图一样，多写一个 sub，写子主题的 id。子主题的 id 写成「主题号-序号」，比如 g6-1、g6-2，不能跟主题号重，也不能跟别的子主题重。别的主题、别的子主题里的数据连到这个子主题的数据时，那一边的 external 写上 sub，页面上点虚框就直接进这个子主题。

**上下文/<名>/业务/模块业务/<主题>.json**（一个主题一份，页面上叫「业务」）

```
{ topic, title, summary,
  tours?: [{ title, note, steps: [{ by, text, concepts?: [概念名], fns?: [功能号] }] }],
  core: [{ title, why, parts?: [概念名],
    sources: [{ heads?: [{ steps }], steps: [{ data, op, by, fn?, event?, topic? }] }],
    targets: [{ op, by, fn?, data, topic? }] }],
  uses?: [{ title, note }],
  purposes: [{ text, from, source?,
    needs: [{ aim, text, cores?: [核心数据名], data?: [数据名], fns?: [功能号], chains?: [内部流程号] }] }],
  intro: { context, duty: [一条一句], concepts: [{ title, note }],
           users: [{ who, aim, steps: [一件一句] }], usual: [一步一句] },
  groups: [{ title, functions: [{
    id, title, called?, does, intent,
    subject: { title, op, from?, to, edits: [一项一句] },
    in: [{ title, by?, note }], out: [{ kind, title, when? }],
    rules?: [一条一句], uses?: [{ flow, step }], source? }] }],
  chains: [{ id, title,
    after: { title, from?, to, when? },
    then: [{ kind, title, from?, to?, when?, note? }] }],
  workflows: [{ id, title, states: [{ id, title, called? }], moves: [{ from, to, label }],
    stages?: [{ title, states: [状态 id] }], note? }],
  asks?: [{ id, q, lean?, options?: [], answer?, answeredAt? }] }
```

要答的问题：

下面的问题照想的先后排：先是背景，再是核心数据和概念，然后是业务目的和更细的目的，最后才是功能。文件里各栏的先后和这个不一样，你照这个先后答完，再照文件的骨架写，各栏照骨架里的先后摆。

- **这块业务所处的情形是什么？**（intro.context）用一两句话写背景：谁出钱、谁办事、谁来查。
- **这个主题的核心数据是哪几样？**（core，一样一条）一样数据算不算核心数据，照角色文件里的判法。一份核心数据里装着别的几样的，那几样写进它的 parts。
  - **它叫什么，为什么是它？**（title、why）title 和概念图里的名字一样。why 用一两句话说为什么是它。
  - **它里面装着哪些概念？**（parts）写概念的名字，一层层往下装着的都写进来；它要和概念图上上下层的线对得上。
- **每样核心数据从哪来、到哪去？**（core 的 sources、targets）问这个问题，是要让没接触过这块业务的人看一张图就知道：这块业务留下什么，它是哪些事一步步攒出来的，它又带出了哪些数据。这张图叫看板，一样核心数据一张。一张看板只讲这一样核心数据从无到有、再到带出别的数据的这一条线：正中是它，左边是把它新建出来的几条来路，右边是它的去处；图上每一站是一样数据，线上是把前一样变成后一样的那件业务。这条线要完整：一条来路从最开始发生的那件事写起，一直写到核心数据，本主题里经过的凭据、申请一站都不跳。会让这条线看不清的都不放上来，它们各有去处：
  - 别的主题里往后的事：去处只写到出本主题的第一站，再往后是那个主题自己的事。
  - 本主题里另一样核心数据自己的来路和去处：来路往前追、去处往后走，碰到另一样核心数据就停在它那里，它有它自己的一张看板。
  - 对这样核心数据自己的改动：哪项功能改了它，写在那项功能的业务数据上；系统到了时间自己做的改动，写进内部流程。
  - 为了看而算出来的数，比如账户还能用多少，是拿实际剩的减去还没付的算出来的：算式里用到的数据，写进做这件计算的那项功能的要用到的数据，怎么算写进规则；其中是概述里的核心概念、又不归哪一样核心数据的，再列进用到的资料。
  - 状态：在状态转换流程里看。
  - 一模一样的几段：只画一遍。
  - **来路怎么写？**（sources，一条来路一项）steps 从最远的一站写到最近的一站：data 是这一站的数据，by 是把它变成下一站的那件业务，用一句话写清谁做了什么；最后一步的下一站就是核心数据。那件业务是哪项功能做的，写功能号 fn。来路的头上不是一样数据、是一件发生了的事的（比如没有凭据，直接记下），那一步的 data 写这件事，再写 event: true。几条来路从某一站起往后完全一样的，合成一条来路：那一站和它后面的写进 steps，前面各不相同的几段写进 heads，一个起点一项，每项的 steps 写到 steps 的第一站为止，不含那一站；各路在合并以后的那几段里有不一样的地方，写进那一段的 by。
  - **去处怎么写？**（targets，一项一条）by 是那件业务，同样写清谁做了什么，data 是去到的数据，fn 是本主题里做这件事的功能号。这里的功能让它新建或改变、数据却归别的主题的，叫交给别的主题的数据：写上 topic，也写 fn。topic 写那个主题在全局图上的名字。
  - **每一步对下一站的数据做了什么？**（op）要让人一眼看出这份数据是多了一份、还在但变了，还是没了。op 写在来路的每一步和每个去处上，只写三个词：创建、更新、删除。每条来路的最后一步是创建。
  - **这块业务还用到哪些资料？**（uses，和 core 并排写）用到的资料不是这里的数据，这里只读它、照它办，比如模板、名录；每条用一句话说它是什么（note）。它和交给别的主题的数据是两回事：交给别的主题的数据是这里的功能让它新建或改变的，写在核心数据的去处里。
  - 概述里的每个核心概念都要在看板上找得到：它是一样核心数据，或者在某一样的 parts 里，或者在 uses 里，或者是来路、去处上的一站。
- **这块业务里有哪些核心概念？**（intro.concepts）每样用一句话说它是什么。
- **这块业务要交出什么？**（purposes）text 是业务目的，一条一句。from 写它对着背景里的哪一句。source 写出处：原料的哪一处，或者人哪一天说的原话。你推出来、还没有人确认的不写 source，你同时在 asks 里问人。
- **每条业务目的往下，是为了达到哪几条更细的目的，各落到哪里？**（purposes 的 needs，一条更细的目的一项）aim 是更细的目的，回答为了什么；text 是做法，用一句话说怎么做到它。cores 写它落到哪几样核心数据上，data 写它落到的别的数据，比如来路上的凭据，fns 写它落到哪几项功能上，写功能号，chains 写它落到哪几条内部流程上，写内部流程号。fns 和 chains 只写本主题自己的号。
- **用一句话说，这块业务做什么？**（summary）不写「这是模块自己的业务逻辑」这类讲文件本身的话。
- **这块业务管什么、不管什么，谁来用，最常走哪条路？**（intro 的 duty、users、usual）这三样和背景、核心概念合起来是业务概述，给人先看懂这块业务再看功能。五样都照「换一家公司来用，这一条还成立吗」来写，不写期限、部门、这家公司自己定的选项：
  - duty 是模块职责：这块业务管什么、不管什么，写成列表，一条一句。
  - users 是使用角色，一人一条：who 是谁，aim 是他用这块业务想做成什么，steps 是他按先后做的几件事，一件一句，每一件都能对上一项功能。
  - usual 是典型流程：最常走的那条路，一步一句，几步就够。
- **最常走的一两条流程，每一步是谁做了什么？**（tours，主要流程速览）问这个问题，是要让第一次看的人先顺着一条线走一遍，知道这块业务平常是怎么办下来的，再去看一样样数据和一项项功能。所以只挑最常走的一两条。一条流程写名字（title）和一句说明（note）；steps 一步一项：by 是做这一步的角色，text 用一句话写他做了什么，concepts 写这一步碰到的概念，fns 写这一步用到的本主题的功能号。别的主题办的那一步照样写进来，不写 fns。
- **这块业务有哪些功能，怎么分组？**（groups）一项功能是业务上的一件事：对一样数据做一种改变。所以你按动的是哪样数据来分组，不按在哪儿做、谁来做；一项功能只做一种事，新增、改名、停用、启用各是一项；找不出它主要动的是哪样数据的，多半是把两项功能合成了一项。
- **每项功能做了什么？**（functions）功能这一页是给没参与的人看的。他不问人就要看懂：这一次想做成什么，动的是哪一份数据，它从什么变成什么，具体动了哪几项，带了什么进来。每一栏你都照「他看了会不会还要来问」来写：他会问「是哪一份」，你就把它说清，比如写「这位客户的账户」，不只写「账户」；他会问「能选什么」，你就把选项列出来。
  - **这项功能叫什么？**（title、called）你从模块负责的业务出发起名，用正式的说法，不照搬页面上的叫法，页面上的叫法写在 called。一项功能做了两件事的，两件事都写进名字。
  - **它做了什么？**（does）用一句话写。
  - **这一次是想做成什么？**（intent，每项都写）intent 是操作意图，用一小段话写，用正式的书面说法，不用口语。你写这项功能为了什么，不把动作再说一遍，比如写「让申请人知道报销单为什么被退回，以便他补齐凭据再交」，不写「发送退回通知」。因为动作在名字和 does 里已经有了，看的人要从这里知道的是为什么要有这项功能。
  - **它主要动的是哪样数据，从什么变成什么？**（subject，每项都写）subject 是业务数据。title 写清是哪一份，里面只带一个概念名，就是这项功能主要动的那一样：页面从 title 里认概念名当主数据，带了两个就认不准，所以限定它是哪一份的话里不再带别的概念名。数据归别的主题的，写成「已发邮件（消息通知）」，括号里是那个主题的名字；不写成「这张订单名下的一封已发邮件」，那样会被认成订单。from 和 to 各写成一句完整的话，主语、宾语都在，新记下的数据不写 from；op 写这项功能对它做了什么：创建、更新或删除，和看板上的写法一样；edits 列出动了它的哪几项，一项一句，写成「名字：逻辑」：冒号前面是概念或者栏的名字，冒号后面是这一项照什么记下、怎么变，比如「状态：草稿 → 已确认」；说的是一个概念里的某一栏的，写成「概念 › 栏：逻辑」。
  - **它要用到哪些数据？**（in，一样一条）title 写数据名；by 写这样数据是谁给的，比如「财务定的」「系统带出的」「申请人填的」，只是指明办的是哪一条记录的那一项不写 by；note 用一句话说清带进来的是什么：是选项的，业务本身固有的几种照列，这家公司自己定的只写「从几种里选一种」，具体哪几种写在流程里；是已有的一条记录的，写带进来的是哪一条；是数字或日期的，写单位。
  - **它顺带留下了什么？**（out）out 只写顺带留下的东西：别的新记录、别的记录的状态改变、对外告知的事；kind 写是哪一种，when 写什么情况下才有。业务数据那一条已经写在 subject 里，不再写进 out。
  - **它守哪些规则，用在哪份流程的哪一步，出处在哪？**（rules、uses、source）rules 只记归模块的规则，一条一句；uses 写这项功能用在哪份流程的哪一步；source 写出处。
- **一样数据变了以后，接着哪几样数据怎么变？**（chains，内部流程）你只写数据怎么变，不写动作：after 是引起它的那样数据的变化，then 是接着变的那几样数据，when 写条件。
- **每个有状态的概念有哪些状态，怎么从一个状态走到另一个状态？**（workflows，状态转换流程）一个概念一份，title 写这个概念的名字，和概念图里的一样，页面靠名字把状态图挂到这个概念后面。states 是它的状态，moves 是从哪个状态走到哪个状态，label 一句话说什么时候这样走。状态很多、一张图看不清的才分段（stages）：一段一项，title 是这一段的名字，states 写这一段里的状态 id，每个状态正好分在一段里。
- **哪些事你拿不准？**（asks，待定）你拿不准的事写成一条待定，带上你的偏向（lean）和几个选项（options）。

和工作台之间的约定：

- 编号：功能号写 f-1、f-2…，在一份里不重复。内部流程，号写 c-1、c-2…。状态转换流程，号写 w-1、w-2…。待定，号写 q-1、q-2…。
- uses 这个栏名有两处，意思不一样：和 core 并排的 uses 是这块业务用到的资料；功能里面的 uses 是这项功能用在哪份流程的哪一步。
- 来路和去处上的 topic：那个主题在别的上下文里的，写成「主题名（上下文名）」。检查工具会查本上下文的主题名对不对得上全局图。
- 页面怎么显示：主题页从上到下五块，每块默认收着，收着时是一行标题加一句提示，点开才展开。
  - 业务概述：三个页签。模块职责，最上面先放背景（context），下面是 duty，一条一行；使用模块的角色（users）；典型流程（usual）。
  - 主要流程速览：一条流程一个页签，下面是它的说明，再下面是流程图。一步一个带编号的框，角色在框的上方，这一步碰到的概念画在它和下一步之间的线上，用到的功能是框下面的标签，点了看那项功能。不写 fns 的那一步画成灰色的虚线框。
  - 核心数据和概念：一样核心数据一组，它装着的概念照概念图上上下层的线缩进排在下面。有同名状态转换流程的概念，名字后面有「状态转换」的标签，点了看状态图；每组顶头那一行有「概念图」的标签。每行后面的一句说明，页面先后取：业务概述里的概念说明、用到的资料的说明、概念定义的头一句。每组最后列出它用到的资料，和交给别的主题的数据。
  - 业务目的及方案：一条业务目的一行，点开是一张表，一行一条更细的目的：左边是 aim，下面的小字是做法；右边是它落到的核心数据、别的数据、功能、内部流程，都能点。不写 source 的业务目的，页面会标「推出来的，等你确认」。最下面列出没有目的落到它上面的核心数据、没有挂上的功能、没有挂上的内部流程。
  - 待定：收着时写有几条没答。
  - 点标签浮出来看的有五种：
    - 核心数据的看板：左边来路，中间核心数据，右边去处，底下一行是用到的资料。中间的框里套着它装着的概念，写了 fields 的列出栏名。来路或去处碰到本主题里的另一样核心数据，那一站能点过去。op 标在那句话的前面，三种颜色不同。别的主题的数据画成虚框。
    - 功能：左边是操作意图和要用到的数据，写了 by 的，by 显示在数据名的上面；中间是业务数据，edits 的每一项一行，前面标创建、更新或删除，新建的写「记下」，更新的写「会改」，写成「概念 › 栏：逻辑」的归到那个概念的格子里；右边是顺带留下的；下面是规则、用在流程的哪一步、出处。
    - 内部流程：从左到右一个个数据变化的框。
    - 状态转换流程：状态图；分了段的上面一排页签，一次看一段。
    - 概念图：只画点开的那一样数据的一块：它自己、它装着的概念、和这些直接连着线的概念。
- 检查工具：
  - 报错的：更细的目的落到的核心数据、别的数据、功能、内部流程找不到；主要流程速览里用到的功能找不到；分了段的状态图里有状态不在、分进了两段或者没有分进哪一段。
  - 提醒的：一条更细的目的没写 aim；一样核心数据没有目的落到它上面（asks 里有一条没答的问题提到了它，就不再提醒）；一项功能、一条内部流程没有挂到哪条目的上；概述里的核心概念在看板上找不到；状态转换流程的名字对不上任何一个概念；用到的资料没写说明；交给别的主题的数据没写功能号；subject 的 title 里认得出不止一个概念名；一项功能的出处和别的主题的功能是同一个代码文件，这多半是放错了主题。
- 人答了以后：待定页面上标红，人点一个选项就是答了，答案写回 answer。答案落进功能、内部流程或状态转换流程以后，你把这条待定整条删掉。

**上下文/<名>/业务/流程/<流程名>.json**（一个主题里的一个阶段一份）

```
{ file, title, topic, summary, parties: [{ id, title, sub }],
  entries?: [{ text, step, flow? }], exits?: [{ text, step, flow? }],
  steps: [{ id, from, to, title, date, data?: [数据名], due?, source?, note?,
            opt?, alt?, case?,
            rules?: [{ id, text, source, status: 待定 | 定了, lean?, options?: [], answer?, answeredAt? }],
            asks?: [{ id, q, lean?, options?: [], answer?, answeredAt? }] }] }
```

要答的问题：

- **这一段有哪些人参与？**（parties）parties 是参与方，写原料里的角色；sub 是名字下面的一句小字，说她是谁、在哪儿用。
- **这一段从哪来、到哪去？**（entries、exits）entries 和 exits 是入口和出口：text 一句话说从哪来、到哪去，step 写接在这一份的哪一步上，入口不一定是第 1 步；flow 写接着的那一份流程。两份流程接上的地方，两边都要写。
- **每一步是谁把什么交给谁？**（steps）from、to 是谁交给谁，title 是这一步做的事，data 是带着的数据，due 是要在多久之内做完，source 是出处。date 是这一步发生在什么时候，照业务的说法写，比如「第 1 天」「交上以后」。
- **哪些步不一定发生，哪些步是几支里只走一支？**（steps 的 opt、alt、case）可能发生的步写 opt，一句话说是什么情况；几支里只走一支的，每一步写 alt（一句话说按什么分开）和 case（这一支是什么情况）。
- **这一步守哪些规则？**（steps 的 rules）归应用落地的规则，一条一条记在流程里触发这条规则的那一步上；归模块的规则不记在这里，记在模块业务里它那项功能的 rules 上。一条规则如果好几步都用到，你把它记在最先触发它的那一步上，别的步在自己的规则里只写一句「照某一步的规则」。待定的规则就是问题，lean 是偏向一句话，options 是几个可选的答法。
- **这一步上还有哪些不是规则的问题？**（steps 的 asks）原料里没说、你又需要知道的事，你把问题记在流程里碰到它的那一步上。流程上的问题，你只记在碰到它的那一步上，不另外开一份问题清单。

和工作台之间的约定：

- 文件名和编号：file 是这份流程的文件名，不带 .json，写成「主题号-两位序号-阶段名」，比如 g4-01-定级与指派；topic 是这一份讲的主题号。旁支的步号写 9a、9b，不动后面的步号。规则的 id 在一份流程里不重复（r-1、r-2…）；问题的号写 a-1、a-2…。
- 页面怎么显示：挨着的几步 opt 或 alt 写得一样，就画在同一个框里。页面照数据卡上的数据在哪个主题，在标题下面列出这一份碰到的主题，再在每张数据卡前面写上主题名、照主题上色。
- 检查工具：两份流程接上的地方，检查工具会查两边有没有对上。
- 人答了以后：待定的规则，人答了写进 answer、status 变定了。问题，答了写 answer。答案落进流程以后收干净：规则照答案改好 text、source 补「某日他答」，去掉 lean、options、answer、answeredAt，只剩一条定了的规则；问题落进步骤或规则以后整条删掉。答案在日志里有，流程上只留没答的问题。
- 先照偏向做的记法：人让你先照偏向做的时候，你暂定的规则不挂成待定：text 照你的偏向写，status 写「定了」，source 写「暂定」，再写上人是哪一天说可以先照偏向做的，不留 lean 和 options。人回来同意了，你把 source 里的「暂定」改成他是哪一天定的。

**共享内核/业务/概念.json**：和概念图一份一样的形状，topic 写「共享内核」。

**项目.json**（上下文地图的框）

```
{ name, contexts: [{ id, name, role, c }], kernel: { concepts: [概念名] } }
```

要答的问题：

- **项目里有哪几个上下文，每个上下文管什么？**（项目.json 的 contexts）role 用一句话说它管什么。
- **哪些概念是几个上下文共用的？**（项目.json 的 kernel）写共享内核里的概念名。

和工作台之间的约定：

- c 是颜色号，只为页面写。

**上下文图.json**（上下文地图的线）

```
{ edges: [{ from, to, kind, name, note? }] }
```

要答的问题：

- **上下文之间靠什么来往？**（上下文图.json 的 edges）kind 是「事件」或「查询」：事件 from 发、to 听；查询 from 问、to 答。

和工作台之间的约定：

- 哪个上下文用了共享内核的哪些概念、各上下文到哪一步，页面从文件夹里数，不用写。

**页面「业务」**：左边栏最上面一条「上下文地图」（一排上下文框、线上是事件或查询的小卡、底下共享内核；表里各上下文到哪一步），下面按上下文折叠：全局图（最上面是整个上下文的背景和每个主题的业务目的，下面一排框、曲线、线上小卡）→ 业务（一个主题一份，从上到下五块：业务概述、主要流程速览、核心数据和概念、业务目的及方案、待定，每块默认收着；核心数据的看板、功能、内部流程、状态转换流程、概念图都是点标签浮出来看；待定标红，点一个答法就是答了，答案写回模块业务的文件）→ 点一个主题进概念图（关系图 + 文字说明；分了子主题的主题先进子主题图，画法和全局图一样，再点进一个子主题看它的概念图，左边栏把子主题缩进列在主题下面）→ 流程（左边栏按主题分组、默认折着；时序图，标题下面一排主题，顶上那排参与方往下滚时钉在最上；入口、出口卡在最左边一列，跟它接着的那一步一样高，点了去接着的那一份；opt、alt 是虚线框，alt 框里横虚线隔成格；点一步亮一步；规则和问题像文字说明一样放在步骤旁边，一条虚线带箭头指到它属于的那一步：待定的规则和没答的问题红色，带偏向和几个选项，点一个就是答了，答案写回流程文件；答了的问题落成规则，和定了的规则一样灰色、同样虚线指过去）；共享内核列它的概念。左边栏流程那行红点加还有几条待答，上下文那行汇总。这一页的页面代码在这支队目录的 `pages/业务/`。
