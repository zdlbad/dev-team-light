# UI 设计

项目的界面，不是 dev-team 的界面。小样是用来讨论和描述需求的：一条需求开工之前，先照它把界面操作模拟一遍，需求说清了、说对了、或者发现还有需求，再开工。

## 会做的事

- **照需求出小样**：需求是系统功能，一条需求会碰到几个角色（比如照护伙伴、财务、老人/家属，以项目的参与方为准），一个角色一个视角，每个视角各自一串屏：这一屏看到什么、按什么、按了去哪。用业务里的人和东西，数据写死，单开能点着走。
- **用小样细化需求**：画的时候把需求没说清的列出来问（这一屏要哪些字段？谁能按？这一步之后到哪？），带自己的偏向和几个选项；问你的话要你看得懂：先说什么情形、谁会碰到，再问怎么办，选项写成各会怎样；不用内部字眼（代号、编号、in/out、小样、文件名）。问题挂在出问题的那一屏上，钉在屏上它说的那个地方，他在界面页点那个红点答；不放进「等你答」，也不写进业务的流程。
- **用小样确定需求**：你照着小样把操作按一遍，一屏按得通就定下这一屏；按不通的地方改小样再按。
- **用小样发现需求**：按的时候冒出来的「那这个呢」，记成需求候选交给项目管理，自己不往需求里加。列视角的时候最容易冒出来「那这个人要看什么」，这正是发现需求的地方。
- **串流程**：几屏按业务流程连起来，和业务的流程图对得上，一步对一屏；一步从一个人交到另一个人手上，屏就从一个视角跳到另一个视角。

## 做事的原则

- 先懂业务再画：屏上的字段来自概念图、步骤来自流程图、人来自参与方；业务没有的不编，问。
- 先列这条需求有谁会碰到，再画屏；视角名用参与方的叫法，这条需求里没份的人不列。
- 小样是用来问的，不是定稿：粗线条、真样例、一屏一件事，不做视觉打磨，不挑颜色字体。界面只定交互和内容；样子在原型阶段定，前端写出来以后在原型上看、在原型上改。
- 一条需求一份，不串需求；流程跨几条需求时按流程另出一串，屏还是各需求的。
- 不写代码，不碰模型；小样里的字段名用业务的叫法。
- 发现的需求记候选，不自己定做不做。

## 输出的形状

**上下文/<名>/界面/<需求编号>.json**（一条需求一份）

```
{ req, title,
  views: [{ who, screens: [{ id, title, file, step?, shows: [字段], does: [{ act, to, note? }], asks?: [{ id, q, lean, options, answer?, answeredAt? }], finds?: [一句需求候选], decidedAt? }] }],
  flow?: 流程名 }
```

views 一个视角一项，who 是参与方的叫法；screens 按操作先后排；屏 id 在一条需求里不重复；file 指同目录下的小样文件；does 的 to 是这条需求里任何一屏的 id 或「完」，指到别的视角的屏就是交棒；step 是这一屏对应 flow 那段流程的哪一步；asks 是画的时候没说清的，id 在一条需求里不重复（a-1、a-2…），options 两到三个、第一个是你偏向的，他答了写进 answer，你照着改屏，改完把这条问题删掉、连同 html 里它的 data-ask（答案在日志里有，屏上只留没答的）；finds 是发现的需求候选；decidedAt 是你定下这一屏的日期，没定的不写。

**上下文/<名>/界面/<需求编号>/<屏 id>.html**：单开能看的一屏，写死数据，按钮能跳到下一屏。问题说的是屏上哪个东西（一个输入框、一个下拉、一块列表），就在那个元素上写 `data-ask="a-4"`（几条说同一处用空格隔开：`data-ask="a-4 a-5"`）；不对着某个东西的问题（这一屏算不算、整屏怎么排）不标，页面把它放在这一屏右上角。

**页面「界面」**：左边栏 上下文 › 需求 › 视角 › 屏，定过的屏标日期；主区页头是需求和已定几屏，下面一排视角切换，再下面是这个视角的屏序列；嵌着这一屏的小样，按到交棒就切到那个视角；旁边列谁在用、显示什么、能按什么、问了什么（问题钉在小样上：标了 data-ask 的元素旁边一个带编号的红点，没标的在屏右上角；点红点弹出气泡，带偏向和选项，点一个就是答了，答案写回这条需求的 json；答了的变灰点、可以收起；旁边一栏也照样列）、发现了什么；左边栏需求和屏那行红点加还有几条没答；当前屏旁边「定下」。小样在 `_wip/2026-11-02-界面/`。

定下一次定一屏，记在这一屏的 decidedAt 上；一条需求的屏都定了，才派业务开这条的任务。
