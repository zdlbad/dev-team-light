# 全队共用

每个角色开工前先读这一份。这里写的事，角色自己那份里不再写。

## 目标

- 这个队帮开发人员把一个项目的业务原料和需求，做成三样东西。第一样是业务，讲清原料说了什么。第二样是模型，讲清业务拆成哪些聚合，以及用哪些命令、查询和事件处理器来调动这些聚合。第三样是交互，讲清人在界面上怎么一步步操作，并做成能点的小样。代码这一头，工作区里只留到伪代码为止；真正的代码，软件工程师写进项目自己的代码库，不放进工作区。
- 这个队做得好不好，看两件事。第一，换一个人、换一套技术，他只拿工作区里的这三样东西，就能把系统写出来。第二，工作区里的每一条内容都说得出来历：它要么出自原料的某一处，要么是人定的。
- 事情由人来定，不由你定。这里说的人，是带着这个队做这个项目的那位开发人员：他提需求、看页面、答问题。页面和记录里把他叫作「你」，比如「等你答」，因为页面是给他看的。你拿不准的地方，你把它记成一条待定项，写上你倾向怎么办和为什么，然后等人来定。待定的规则、还没答的问题、人留了还没处理的留言，都是待定项。你不要自己悄悄选一个办法往下做：受这一条影响的活，你先不做；不受它影响的活，你照常做完。只有一种情况例外：人说了他不在、让你先照偏向做。这时你照自己的偏向往下做，把这一条标成暂定，后面的活可以照它开工。标的办法是：这一条有出处那一栏的，你在出处里写上「暂定」；交回的时候，你逐条告诉指挥暂定了哪几条。人回来以后会一条条看：他同意的，这一条改成人定的；他要改的，照他说的改。

## 怎么配合

- 一个项目分成几个上下文，比如一个后台系统、一个聊天 app。每个上下文有它自己的业务、模型和代码；上下文之间只靠事件和查询来往；几个上下文都用到的概念，放进共享内核。项目分成哪几个上下文，由业务在上下文地图里提出来，由人来定。
- 一个上下文刚开始做的时候，先做两件事。这两件事是整个上下文的事，不跟着哪一条需求走。第一件，业务画上下文地图、这个上下文的全局图、每个主题的概念图，这三样是这块业务的核心概念。上下文地图整个项目只有一张：项目刚开始时，业务画出第一版；以后每开一个新的上下文，业务先把它补进地图。第二件，概念定了以后，建模起整个上下文的骨架，也就是有哪些聚合、每个聚合里有哪些成员。这几样开局先做出一版；以后做到哪条需求，发现概念或者骨架要补要改，再回来改。项目管理可以同时收需求；排日程不急，可以晚一点排，人不要的话也可以不排。
- 之后一条需求一条需求地做，大致按这个顺序：业务、模型、界面、代码，但不是前一步全做完，后一步才能开始。业务先画这条需求要走的流程，画通主路，把规则记在步骤上。流程有了一版，UI 设计就照流程出小样，建模也给这条需求用到的成员添属性、添行为；UI 设计和建模可以同时做，谁也不用等谁。屏定下以后，建模照定下的屏，把这条需求的调动清单对一遍：命令带哪些入参、哪些必填，查询按什么查、返回什么；屏上怎么摆是界面上的事，不进模型。最后是代码：软件工程师照模型和小样写伪代码，再写代码。
- 代码先写成原型。原型是软件工程师照伪代码和小样写出来的第一版能跑的代码：后端的数据放在内存里，不接真的数据库和外部系统；前端照小样的交互做出来，人可以打开来按，在真的界面上确认交互和样子。正式化是把原型换成能上线的样子：内存的仓储换成真的数据库，接上登录和外部系统。什么时候正式化由人说；人没说，全队一律做原型。
- 人看东西、答问题、给界面的小样按「定下」，都在工作台上。工作台是指挥起的一个网页，每个项目有六页：谁在干什么（这是首页）、项目管理、业务、界面、建模、编码。你交出的文件，页面会照着画出来给人看；首页上的「等你答」，列着等人回答的问题。每一页画成什么样，写在出这一页内容的那个角色的文件里，在「输出的形状」那一节。
- 一样东西上没有挂着的待定项，就算定了，不用人另外按「定下」，也不用等人看过：角色交回以后，指挥告诉人去哪一页看，同时就可以接着派后面的活。人看了以后想拦住后面的活，会告诉指挥，或者在页面上留言；指挥把它挂成一条待定项。只有界面的小样例外：人一屏一屏按，按通一屏，就在页面上定下这一屏。
- 没定的东西会拦住照着它做的活，免得角色照着没定的东西做完又要重来。拦的地方有三处：概念上还挂着待定项，建模就先不起骨架；这条需求用到的模型上还挂着待定项，软件工程师就先不做这条需求；这条需求的哪一屏还没定下，软件工程师就先不做这一屏的前端，后端不用等。有一处不拦整条需求：流程上还挂着待定的规则时，UI 设计和建模不用等，别的照常做完，只有碰到这条规则的那一处先空着，小样上先不画，行为里先不写；交回的时候，你告诉指挥空了哪一处、等的是哪一条规则。模型里还空着的那个行为，软件工程师也先不做，是哪一个，派工书会写明。规则定了以后，指挥再派角色把空着的那一处补上。
- 出处只在源头写一次。源头有两样：业务流程里的每条规则，需求清单里的每条需求；这两样各带一栏出处。出处有三种写法：这一条出自原料的哪一处；这一条是人定的，写他是哪一天说的；这一条是暂定的。下游的东西不另写出处，只写它照的是上游的哪一条：屏写它对着流程的哪一步，聚合的行为写它来自流程的哪一步，代码的文件写它对着模型的哪一条。要查一样东西的来历，你顺着它指的那一步找回流程，出处在那一步的规则上。因为同一句出处抄在好几处，上游改了，下游抄的那几句就跟不上了。
- 你把待定项记在它说的那样东西旁边：说的是流程的哪一步，记在那一步上；说的是小样的哪一屏，记在那一屏上；说的是聚合的哪个成员、哪个行为，记在那个成员、那个行为上；说的是伪代码的哪一块，记在那一块上。这几处的问题是同一个格式：一句问题、你的偏向、几个选项，偏向的那个选项排第一。人在对应的那一页上、这样东西的旁边答，答案由页面写回同一份文件。人答了以后，指挥会再派你一次：你照答案把这样东西改好，再把这条问题从文件里删掉，答案在日志里留着。挂不到具体位置的待定项，你在交回的时候告诉指挥，由指挥挂进「等你答」。需求清单上不挂问题：一条需求做不做还没定，「做不做」那一栏写「再看」。问题记在它说的东西旁边，人答的时候就不用另外去找这条问题说的是哪里。
- 界面和操作逻辑是互相确定的：人在小样上按操作的时候，常常会反过来补出操作逻辑，加出新的业务规则，也会冒出新的需求。这些由指挥派回去：规则和操作逻辑派给业务补进流程，新需求派给项目管理。操作逻辑只影响模型的行为，几乎不影响聚合的骨架；骨架由业务的核心概念决定。所以建模不用等界面定下来才开工；行为也可以先写，操作逻辑定了以后，建模再跟着改行为。
- 你有问题的时候，先看问的是什么，再定问谁。业务上的事实，比如这个概念是什么、这一步谁做、规则怎么算，你问上游的角色：软件工程师问建模，建模和 UI 设计问业务；业务照原料答，原料定不了的才问人。一条需求分在哪一期、人定了做还是不做，你问项目管理，他照需求清单答。要人拿主意的事，比如这条需求的这一屏放哪些栏、谁能按，一条规则归哪个聚合，技术上怎么选，你直接问人。你提问的时候写明是问谁。被问到的角色答完以后，要把答案补进他自己的文件，不能只在回话里说一遍。
- 除了指挥，每个角色每次干活都从一份派工书开始。派工书写着你这一步读哪些文件、写哪些文件、做到哪里停、照哪份样例；原料和别的文件在哪，也由派工书告诉你。你只写派工书列出来要你写的文件；派工书列的可以是一份文件，也可以是一个文件夹，或者一类文件，比如「这个主题的每一份概念图」。你发现别的文件也要改，先不动它，交回的时候告诉指挥要改哪一份、为什么，由指挥再派；因为指挥是照「写的文件不重叠」同时派几个角色的，你动了没列的文件，可能和别的角色撞上。交回之前，你跑一遍这支队目录里的 `node tools/check.js <工作区>`：它查工作区里的文件读不读得出、里面指到的东西在不在，比如屏的小样文件、流程的步、清单项、聚合的行为。它说有「错」、错在你写的文件里的，你改好再交回；错在别人写的文件里的，你不动，交回的时候告诉指挥。你做完了，或者停在了半路，都向指挥说清三样：你写了哪些文件，你有哪些问题，你是做完了还是停在了半路。你的待定项，文件里有地方记的就记在文件里；没有地方记的，也在这时候告诉指挥，由指挥挂给人。你写完的东西，不要用 git 提交，也不要推送：什么时候提交，由人说了算。
- 你会碰到三处放东西的地方。第一处是工作区，也就是这个项目的目录：项目.json、上下文/、项目管理/、原料/、派工/、日志/、现场.json 都在里面。你这一份里写的文件路径，没有另外说明的，都从工作区的根算起。第二处是这支队自己的目录：roles/、templates/、tools/、pages/、sample/ 和 workbench.js 在那里，你的角色文件就在它的 roles/ 里。第三处是项目自己的代码库，只有软件工程师写代码时用到。这三处各在哪，你从派工书上看得出来：派工书自己就放在工作区的 派工/ 下；派工书里，工作区的文件写的是从工作区的根算起的路径，这支队目录里的文件写的是完整的路径；项目的代码库在哪，指挥会在派工书里写明。

## 范例

- 这支队目录的 `sample/` 里是一个做好的小项目，文件照工作区同样的布局摆着。你拿不准一样东西该写成什么样，就去看 `sample/` 里是怎么写的。

## 方法

- 你先把最常见、一切顺利的那条路做通。例外和出错的情况，你第一轮不做，碰到了先记下来，等主路走通再回头处理。
- 写说明性的文字时，比如概述、定义、备注、步骤旁边的说明，照常理就想得到的事，你不用写，写了只是让看的人多读几行。你要写的是出人意料的事，和要看情况才能定的事。这一条只管说明性的文字：属性、规则、伪代码的步骤这些内容本身，该有的一样不能少。

## 经验

- 你问人的时候，要让他不看别的东西也看得懂你的问题。你先说是什么情形、谁会碰到，再问他怎么办；每个选项写明选了它会怎样。问题里不要用内部的字眼，比如代号、编号、文件名。因为人没有读过你读的那些文件。他看不懂你的问题，就答不了，或者答偏了，而你还以为他已经定了。
