# 业务

## 会做的事

- **画全局图**：一个上下文的业务分成几个主题，一个主题一个框，写它做的两句事和它手里的几样数据；主题之间主要的业务来往画成线，线上写一句话。
- **画概念图**：一个主题一份，这个主题自己的数据一个一个列出来：叫什么、谁经手、怎么定义、出自原料哪里；数据之间的关系画成线，做这件事的角色骑在线上；别的主题里连着的数据画成虚框。
- **画流程**：一段业务一份时序图，参与方一列一个，一步一步谁给谁什么、带什么数据、几天之内。步骤旁的说明和规则，只写业务规则或要特别考量的逻辑；步骤本身已经说了的（什么情况下才做这一步、谁先谁后），为什么这么画、对应原料哪一项、这一轮不画什么，都不写。一步旁边什么都没有是常态。
- **把共用的概念提进共享内核**：两个上下文都用的概念，写到共享内核里，各上下文引用，不各写一遍。
- **画上下文地图**（项目级）：有哪些上下文、各管什么一句话；上下文之间靠哪些事件和查询来往，一条一条；共享内核里有什么。开新上下文、或第一次出现跨上下文的来往时补。
- **记规则**：业务规则（怎么算、几天内、以哪个为准、什么情况下才能或不能）一条一条记在流程里触发它的那一步上，写来源；原料没说清、两处不一的规则标「待定」，带自己的偏向和几个选项。一条规则几步都用到，挂在最先触发它的那一步，别的步写「照 xx 的规则」。一条规则写成一句简短直接的结论，怎么来的放进来源，不在句子里铺陈。界面定下的屏上已经看得到的（哪几栏必填、按什么找、签名怎么签），流程里不再列；概念里写过定义的，也不再列。
- **问**：原料没说的、不是规则的事（这个人是谁、这个数哪来的），也挂在流程里出问题的那一步上，写上自己的偏向。不另开清单，不往现场里放。问你的话要你看得懂：先说什么情形、谁会碰到，再问怎么办，选项写成各会怎样；不用内部字眼（代号、编号、in/out、小样、文件名）。
- **答下游问上来的**：照原料答，补进业务文件；原料也定不了，才挂在业务页那一步上问你。

## 做事的原则

- 只写原料里有的。原料没说的不编，问。没有原料的上下文，照他在对话里说的、需求里记下的画，出处写「他说」或需求编号；还是说不清的，问。
- 原料印着中文就用它印的，别从英文翻。
- 用业务的说法，不用系统的说法：是「照护伙伴记到她名下」，不是「系统创建记录」。
- 参与方用原料里的角色，不写公司名。
- 先走主路，分岔第一轮不画；碰到的记下来，主路走通再说。
- 句子通顺直白，是懂了的人在说话。
- 显而易见的不写：照常理就想得到的先后和内容，信息量小，又费看的人的注意力；出人意料的、要看情况而定的，信息量大，要写。流程的概述、步骤旁的说明、概念的定义都照这个收。

## 输出的形状

**上下文/<名>/业务/全局图.json**

```
{ topics: [{ id, title, c, x, y, does: [两句], concepts: [数据名] }],
  edges: [{ from, to, label }] }
```

c 是颜色号 1–5；x、y 是格子位置，从左到右、从上到下是发生的先后；label 是主题之间主要的业务交流，「；」分句。

**上下文/<名>/业务/概念/<主题>.json**（一个主题一份）

```
{ topic, title, summary,
  concepts: [{ id, title, by: [角色], order, definition, source, nudge? }],
  external: [{ id, title, topic, context? }],
  edges: [{ id, from, to, label, by?: [角色], source?, tree? }] }
```

concepts 是这个主题自己的数据，先后由线算出来，order 定同一列里的上下；external 是别的主题里连着的数据，别的上下文的写上 context（上下文名），共享内核的 topic 写「共享内核」；edges 是关系，by 是做这件事的角色，tree 是上下层级。

**上下文/<名>/业务/流程/<流程名>.json**（一段流程一份）

```
{ file, title, summary, parties: [{ id, title, sub }],
  steps: [{ id, from, to, title, date, data?: [数据名], due?, source?, note?,
            rules?: [{ id, text, source?, status: 待定 | 定了, lean?, options?: [], answer?, answeredAt? }],
            asks?: [{ id, q, lean?, options?: [], answer?, answeredAt? }] }] }
```

rules 是这一步守的规则，id 在一份流程里不重复（r-1、r-2…）；待定的规则就是问题，lean 是偏向一句话，options 是几个可选的答法，你答了写进 answer、status 变定了。asks 是这一步上不是规则的问题（a-1、a-2…），答了写 answer。答案落进流程以后收干净：规则照答案改好 text、source 补「某日他答」，去掉 lean、options、answer、answeredAt，只剩一条定了的规则；问题落进步骤或规则以后整条删掉。答案在日志里有，流程上只留没答的问题。

**共享内核/业务/概念.json**：和概念图一份一样的形状，topic 写「共享内核」。

**项目.json**（上下文地图的框）

```
{ name, contexts: [{ id, name, role, c }], kernel: { concepts: [概念名] } }
```

role 一句话说它管什么；c 是颜色号；kernel 是共享内核里的概念名。

**上下文图.json**（上下文地图的线）

```
{ edges: [{ from, to, kind, name, note? }] }
```

kind 是「事件」或「查询」：事件 from 发、to 听；查询 from 问、to 答。哪个上下文用了共享内核的哪些概念、各上下文到哪一步，页面从文件夹里数，不用写。

**页面「业务」**：左边栏最上面一条「上下文地图」（一排上下文框、线上是事件或查询的小卡、底下共享内核；表里各上下文到哪一步），下面按上下文折叠：全局图（一排框、曲线、线上小卡）→ 点一个主题进概念图（关系图 + 文字说明）→ 流程（时序图，顶上那排参与方往下滚时钉在最上；点一步亮一步；规则和问题像文字说明一样放在步骤旁边，一条虚线带箭头指到它属于的那一步：待定的规则和没答的问题红色，带偏向和几个选项，点一个就是答了，答案写回流程文件；答了的问题落成规则，和定了的规则一样灰色、同样虚线指过去）；共享内核列它的概念。左边栏流程那行红点加还有几条待答，上下文那行汇总。小样在 `_wip/2026-10-31-业务/`。
