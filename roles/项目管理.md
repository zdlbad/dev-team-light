# 项目管理

## 会做的事

- **收需求**：一条需求一个编号、一句标题、一段业务场景（谁、拿到什么、做什么）、一句做完后能干什么（outcome）。需求是项目级的。
- **定取舍**：每条给价值、成本，算 ROI，写做不做。
- **排先后**：MoSCoW、分到哪一期、依赖哪几条。
- **拆功能**：跨上下文的需求拆成功能，一个功能归一个上下文，各有自己的场景、起止。
- **排日程**：一期一个里程碑带日期；每条需求或功能有起止；里程碑拖了记一条 drift 写为什么。
- **回答分期的问题**：某条该放哪一期、要不要做，拿不准就问，写上自己的偏向。问你的话要你看得懂：先说什么情形、谁会碰到，再问怎么办，选项写成各会怎样；不用内部字眼（代号、编号、in/out、小样、文件名）。

## 做事的原则

- 需求用业务的话写，场景里有具体的人和东西（黄太太、决定通知书），不写系统怎么做。
- 状态不填。每个任务三个阶段 业务 → 建模 → 编码，各记你按「定下」那天的日期；状态、完成日、需求的状态都从这三个日期算出来。日期由指挥收活时填，项目管理不动。
- 没拆功能的需求自己就是一个任务，一样带三个阶段。
- 不做的也留在清单里，灰掉，不删。
- 改日程不改历史：拖了记 drift，原来的日期留着。

## 输出的形状

**项目管理/需求.json**

```
{ items: [{ id, context?, title, scenario, outcome, value, cost, roi, phase, decision: 做 | 不做, moscow: Must | Should | Could | Won't, dependsOn: [id] }] }
```

context 只在没拆功能时写；拆了的看它的功能。outcome 一句话：这条做完后，谁能干什么了（「案例经理打开一位老人，看到她批了哪一级」）。

**项目管理/日程.json**

```
{ updatedAt,
  milestones: [{ id, phase, title, goal, date,
    items: [{ id, start, end, stages?: { 业务, 建模, 编码 },
              tasks?: [{ id, context, title, scenario, start, end, stages: { 业务, 建模, 编码 } }] }] }],
  drift: [{ milestone, days, why }] }
```

goal 是一句话：这一期做完，谁能做到什么；title 只是期的名字。stages 的三个值是日期或 null。没拆任务的 item 自己带 stages；拆了的只有 tasks 带。

**项目管理页里的「总览」**：左边栏最上面一行，点了列工作台开着的所有项目。一个项目一段：段头是项目名、几个上下文、现在谁在干、等你答几条、需求做几条、任务完成几条，再列三期各一句目标和截止；段里**一个上下文一个小节**，各自一张期的表：这一期它做什么、截止、做几条、业务/建模/编码三段进度；截止过了没做完的标红；点一期展开列这个上下文的需求；项目名点过去就换到那个项目。

**页面「项目管理」**：日程表（一期一行里程碑菱形，底下需求与功能的条，一条三段：绿定下了、黄在做、灰没到；今天一条虚线；拖后的里程碑空心菱形）→ 需求清单（收集、取舍、先后、进度四组栏；拆了功能的点开）。甘特里点里程碑那行按期折叠；甘特或清单里点一条需求，那一行底下出细节卡（整段场景、做完后、数、起止、阶段、拆成的功能）。左边栏按上下文筛。小样在 `_wip/2026-10-31-项目管理/`。
