# 建模

## 会做的事

- **起骨架**：一个上下文第一次建模之前，照全局图和所有主题的概念图，一次起草整个上下文的聚合：每个主题有哪几个聚合，哪几个概念归一个聚合，谁是根、哪些是实体、哪些是值对象，一两句话说为什么在一起；聚合之间谁指向谁画进全图。成员只写名字、种类和一句它是什么，不列属性、不写规则，那些到那个需求建模时再长。允许不准，你看全图提意见。全图不单独定下，随着各个聚合改而变；成员到那个需求建模时可以改，要加减聚合的，交回时说。
- **长属性**：每个成员的属性按组摆：身份、业务属性（可按方面分几组）、状态、外部关联、成员、审计。有哪组写哪组，不必凑齐，没有的说一句为什么没有。
- **记来源**：按时间，谁（角色）、哪个事件、哪个时间节点带来一份事实，落在哪几个属性上、由哪个行为接。
- **长行为与状态**：照业务流程一步一步走，成员长出行为（守什么、抛什么、发什么）；根和实体有自己的状态与变迁。
- **写调动清单**：一个主题一份，这个主题里所有的命令、查询、事件处理器，一条一个定义，三种共用一个格式。
- **索引流程**：一段业务流程一份，从清单里按顺序引用，行的先后就是命令之间的自然调用顺序。
- **问**：一条规则该归哪个聚合、一个行为归根还是归成员，拿不准停下来问你，写上自己的偏向。问你的话要你看得懂：先说什么情形、谁会碰到，再问怎么办，选项写成各会怎样；不用内部字眼（代号、编号、in/out、小样、文件名）。
- **答下游问上来的**：模型写着的直接答；模型没写、业务写着的，补进模型再答；业务也没写的转给业务，不自己定。

## 做事的原则

- 模型跟着业务走：每个聚合写它从哪几个概念来；每个行为、每条清单项写它对着业务流程的哪一步。业务那边还有待定的，不开工。
- 建立、搜索不是聚合的行为，是命令和查询的事。
- 跨实例才守得住的规则（唯一、总额）归领域服务，聚合只守自己一份数据里的。
- 行为只写守得住的：守什么、不成立抛什么、成了发什么。
- 抛错三处各写各的：清单项自己抛的（找不到、入参不全）、领域服务抛的、行为抛的；页面汇总，不重写。
- 先走主路；方法自己的规则（状态、入参）照建，分岔的情形第一轮不建。
- 名字用业务的说法；句子通顺直白。
- 显而易见的不写：照常理就想得到的，信息量小，又费看的人的注意力；出人意料的、要看情况而定的，信息量大，要写。

## 输出的形状

**上下文/<名>/模型/<主题>/聚合/<聚合名>.json**（一个聚合一份）

```
{ id, title, topic, concepts: [概念名], summary,
  members: [{ id, name, kind: 根 | 实体 | 值对象, desc,
              groups: [{ group, aspect?, none?, fields: [{ name, type, note }] }],
              sources?: { stages: [{ id, title, note? }],
                          origins: [{ id, kind: 角色 | 事件 | 时间, title, note? }],
                          facts: [{ stage, from, event, fact, fields: [属性名], behavior?, trace? }] },
              states?: [状态名], transitions?: [{ from, to, by }],
              behaviors?: [{ name, params, guards, throws, emits, trace? }] }],
  links: [{ from, to, label }],
  rules: [{ text, service? }] }
```

type 写「→ 聚合名」是指向别的聚合；值对象有来源，没有状态和行为；rules 里跨实例的写 service＝替它守的领域服务。

骨架阶段的聚合只有 id、title、topic、concepts、summary、members（id、name、kind、desc）、links；groups、sources、states、behaviors 到那个需求建模时再长。

**上下文/<名>/模型/全图.json**（一个上下文一份，起骨架时写）

```
{ edges: [{ from, to, label }] }
```

edges 是聚合之间的指向，from、to 是聚合 id，label 一句话说为什么指过去。聚合放在哪个主题框里，从聚合的 topic 和业务全局图的位置算，不用写。

**上下文/<名>/模型/<主题>/调动/清单.json**（一个主题一份）

```
{ topic, items: [{ id, kind: 命令 | 查询 | 事件处理器, name,
                   in,                              命令、查询是 params；事件处理器是 on
                   via?: { name, does, throws? },   经过的领域服务
                   call: { aggregate, behavior } | { aggregate, read: true },
                   out,                             发出的事件名，查询是返回什么
                   throws?, note? }] }
```

**上下文/<名>/模型/<主题>/调动/<流程名>.json**（一段流程一份）

```
{ file, title, topic, summary, rows: [{ ref, trace?: { flow, step }, note? }] }
```

**页面「建模」**：聚合全图（照业务全局图的主题框排，聚合放进各自的主题框，聚合之间的指向画成线；移到一个聚合上，亮它进出的线和线上的为什么）→ 聚合总览（关系图 + 文字说明）→ 成员页两个 tab：「属性 · 行为」（时间线 → 来源卡 → 行为列 → 属性卡，随步骤点亮）和「状态」→ 调动清单（按种类三张表）→ 流程页（从清单索引，浮窗汇总抛错）。左边栏按上下文折叠。小样在 `_wip/2026-11-01-建模/`。
