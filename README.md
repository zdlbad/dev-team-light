# dev-team-light

dev-team-light 是一个轻量的、模型驱动的开发团队，由六个角色组成，每个角色是一个 AI 智能体。指挥把活一步一步派给角色；你在页面上看角色交回的东西，答角色的问题。事情由你来定，不由角色定。

## 角色

每个角色开工前先读 [roles/team.md](roles/team.md)，再读它自己那一份。`roles/team.md` 写全队共用的事：这个队的目标、角色之间怎么配合、全队的方法和经验。每个角色有两份：`roles/<角色>.md` 只讲怎么想，写职责、方法、经验；想清楚的东西怎么写进文件，单放在 `roles/写的样子/<角色>.md`，角色想完、动笔之前读。业务角色的 [roles/业务.md](roles/业务.md) 最后一节是「要回答的问题」，是帮它弄懂业务的那几个问题。

| 角色 | 管什么 | 文件 |
|---|---|---|
| 业务 | 上下文地图、全局图、概念图、模块业务、流程 | [roles/业务.md](roles/业务.md) |
| 项目管理 | 需求清单、日程、里程碑 | [roles/项目管理.md](roles/项目管理.md) |
| 建模 | 聚合、调动清单与流程 | [roles/建模.md](roles/建模.md) |
| UI 设计 | 项目界面的小样：写代码之前，你照着小样把操作按一遍，用来细化、确定、发现需求 | [roles/UI 设计.md](roles/UI%20设计.md) |
| 软件工程师 | 规范、技术选型、文件结构、伪代码、代码 | [roles/软件工程师.md](roles/软件工程师.md) |
| 指挥 | 提议下一个任务、派活、收活、记现场、给你看页面 | [roles/指挥.md](roles/指挥.md) |

## 一个项目长什么样

```
<项目>/
  项目.json                         上下文有哪些、共享内核里有什么（业务画上下文地图时写）
  上下文图.json                     上下文之间的事件与查询（业务写）
  原料/                             业务原料，角色只读；不进 git
  项目管理/需求.json  日程.json
  代码/规范/全局结构.json            整个项目一份：用的人、前端、后端、存储、外部系统，谁找谁（软件工程师写）
  共享内核/业务/概念.json
  上下文/<名>/业务/   全局图.json  概念/<主题>.json  模块业务/<主题>.json  流程/<流程名>.json
  上下文/<名>/界面/   <需求编号>.json  <需求编号>/<屏 id>.html      UI 设计写，一条需求一份，里面按视角分屏
  上下文/<名>/模型/   全图.json  留言.json                         聚合之间谁指向谁；你在建模页属性后面留的话
  上下文/<名>/模型/<主题>/   聚合/<聚合名>.json  调动/清单.json  调动/<流程名>.json
  上下文/<名>/代码/   规范/{结构设计,文件命名,技术选型}.json  结构.json  伪代码/<文件路径>.json  原型.json
  现场.json  派工/<日期>-<序号>.json  日志/<日期>.jsonl
```

项目下面一层是上下文（比如 样例系统、聊天 app、排版系统），各有自己的业务、模型、代码；共用的概念写进共享内核；上下文之间只靠事件和查询来往。

这个目录是工作区，里面只留到伪代码。代码和测试，软件工程师写进项目自己的代码库，不放进工作区。

## 思路

先搞懂业务，才能说明白、听明白功能和需求。所以顺序是业务、模型、界面、代码。这个顺序不是前一步全做完，后一步才能开始：

- 业务的核心概念最先定。概念定了，建模就能起整个上下文的骨架，也就是有哪些聚合、每个聚合里有哪些成员。
- 界面和操作逻辑是互相确定的。你在小样上按操作的时候，常常会反过来补出操作逻辑，加出新的业务规则，也会冒出新的需求。操作逻辑只影响模型的行为，几乎不影响骨架，所以建模不用等界面定下来才开工。
- 工作区里只留到伪代码，真正的代码在项目自己的代码库里。换一个人、换一套技术，他只拿工作区里的业务、模型、交互这三样，就能把系统写出来。
- 事情由你来定。角色拿不准的地方，它记成一条待定项，写上它的偏向和理由，等你定。一样东西上没有挂着的待定项，就算定了：你不用另外按「定下」，指挥也不等你看过，就接着派后面的活；你看了想拦住，就在对话里告诉指挥，或者在页面上留言，指挥会把它挂成一条待定项，照着这样东西做的活先停下。只有界面的小样，要你一屏一屏按「定下」。

## 怎么走

一个上下文刚开始做的时候，先做两件事。这两件事是整个上下文的事，不跟着哪一条需求走：

1. 业务画上下文地图、这个上下文的全局图、每个主题的概念图。
2. 概念定了以后，建模起整个上下文的骨架。你在建模页的聚合全图上看。

这几样先做出一版；以后做到哪条需求，发现概念或者骨架要补要改，再回来改。项目管理可以同时收需求、定取舍；排日程不急，你不要日程的话也可以不排。

之后一条需求一条需求地做：

1. 指挥照需求清单和日程提一条需求，你说做，指挥才派。
2. 业务画这条需求要走的流程：先画通主路，把规则记在触发它的那一步上。
3. 流程有了一版，UI 设计照流程出小样，建模给这条需求用到的成员添属性、添行为。这两样可以同时做。流程上还有待定的规则时，这两个角色不用等：别的照常做完，只有碰到这条规则的那一处先空着，等你定了再补。
4. 你在「界面」页照着小样把操作按一遍。一屏按得通，你就定下这一屏；按不通的地方，UI 设计改小样，你再按。你按的时候冒出来的事，指挥分三种派回去：业务规则和操作上的改动，派给业务补进流程；新的需求，派给项目管理记成一条；这一屏本身要改，派给 UI 设计。
5. 屏定下以后，建模照定下的屏，把这条需求的调动清单对一遍：命令带哪些入参、哪些必填，查询按什么查、返回什么。屏上怎么摆是界面上的事，不进模型。
6. 软件工程师照模型和小样出文件结构、写伪代码；伪代码上没有挂着的待定项了，他再写代码。还没定下的屏，他先不做这一屏的前端；模型里因为等规则还空着的行为，他也先不做。一个上下文第一次走到这一步之前，软件工程师先定规范。
7. 代码先写成原型：后端的数据放在内存里，前端照小样做出来，你可以打开来按。什么时候正式化（换成真的数据库，接上登录和外部系统），由你说。一条需求算做完，是软件工程师交回了代码、测试跑过、原型打得开。

每一步，角色交回以后，指挥先把画出来的图截图看一遍（`node tools/shot.js`），把遮挡、重叠的地方调好，再告诉你去哪一页看。角色的问题挂在出问题的那一页上：业务的问题挂在流程的那一步上，你在业务页答；UI 设计的问题挂在小样的那一屏上，你在界面页答；建模的问题挂在聚合的成员或者行为上，你在建模页那个成员的页上答；软件工程师的问题挂在伪代码的那一块上，你在编码页那一块的下面答；首页「等你答」告诉你哪一页还有几条。出处只在源头写：流程里的每条规则、需求清单里的每条需求各带一栏出处，下游的屏、聚合、伪代码只写它照的是上游的哪一步、哪一条。

平时角色拿不准就等你定，后面的活先不开。你说了「我不在，先照偏向做」，角色才照自己的偏向往下做，并且把这一条标成暂定；你回来以后一条条看。

## 工作台

```
node workbench.js <项目目录> [<项目目录>…] [--port 4870] [--now "2026-11-09 16:20"]
```

一个地址，可以开好几个项目，每个项目六页：总览、项目管理、业务、界面、建模、编码（地址 `/<项目目录名>/<页>`，首页跳到第一个项目的「总览」）。首页是你一进来就看的：「等你答」放角色问你的，「等你定」列界面的小样里还没按定下的屏，一条需求一行，点一条去那一屏按；进度一个任务一条四段（业务、建模、界面、编码），做到哪一段是工作台从日志和屏算的，不用谁去填；只看当期（今天落在哪一期），别的期在项目管理页看，一屏只放眼下要你动手的。项目管理页左边栏最上面的「总览」把开着的项目一页列全：每个项目几期、每期的目标和进度，项目名点过去就换项目。六页后面的「原型」照各上下文的 代码/原型.json 链到原型，圆点说它开没开。编码页上「已写」「有测试」的标记和代码预览，读的是 结构.json 里列着的文件，从它的 base 算起（比如 `../packages`，指到项目自己的代码库）；没写 base 就从 `上下文/<名>/代码/` 算起。页面的代码在 `pages/<页名>/小样.html`，单开也能看（用里面写死的样例数据），在工作台里数据从项目目录读出来注进去（`lib/project.js` 管读与写）；页上按「定下」「答」「留言」写回那个项目的 上下文/…/界面、上下文/…/业务/流程、上下文/…/模型/留言.json、现场.json 和 日志/。「定下」只在界面页上有，一次定一屏。你按「定下」、答问题的时候，工作台会核对你看到的是不是现在这一版：页面开着的时候角色改过这一屏或这条问题，它不记，提示你刷新再看一遍。角色正在改的那一份小样或流程，页面顶上会写明谁在改，这一份先按不了，等它交回。`--now` 把「现在」钉在某个时刻，对着样板项目看页面用。

`sample/` 是一个做好的小项目：六页里写死的样例数据按上面的布局落成的，`node tools/export-fixture.js` 重新生成；角色拿不准一样东西写成什么样就看它，`node workbench.js sample` 可以对着它看页面。它要过得了 `node tools/check.js sample`。

`templates/` 是软件工程师定规范时拿来的默认，形状和项目里存的一样：全局结构一份，技术选型一份，结构设计和文件命名各两份（后端一份、前端一份）。`pages/` 里每一页的文件夹带一个 `check.js` 能跑；`node tools/check.js <项目目录>` 查一个项目里角色交出的文件有没有硬伤：读不出的 JSON、指不到的屏和步、缺的小样和伪代码、子主题和它的概念文件对不上、模块业务的号重复或指着的流程步不在、两份流程的入口出口没对上；角色交回之前跑，指挥收活时再跑。`node tools/scene.check.js` 查指挥记现场用的 `tools/scene.js`，`node tools/workbench.check.js` 查工作台写回文件的那几样，`node tools/check.check.js` 查 `tools/check.js` 自己。截图工具 `tools/shot.js` 和编码页的检查要用机器上的 Chrome 或 Edge，Windows、macOS、Linux 上常见的安装位置都找（找法在 `tools/browser.js`，`node tools/browser.check.js` 查它）；装在别处的，用环境变量 `DEV_TEAM_BROWSER` 写明浏览器可执行文件的完整路径。
